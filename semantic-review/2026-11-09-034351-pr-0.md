# Native automatic recording through a microphone foreground service

The change moves Android call-state monitoring and recording out of the React Native lifecycle and into `CallMonitorService`, with a native SharedPreferences switch controlling both service startup and recording. Recordings are inserted into `MediaStore` as pending rows under `Music/Call Recordings`, finalized at IDLE, and left for the existing discovery/upload pipeline. The legacy `CallRecorderPackage` is no longer registered, so the app shell no longer has two active recorder owners. The release Kotlin compilation succeeds with targetSdk 36, but the implementation does not yet meet the requirement that ON capture every complete OFFHOOK call.

Watch for: **confirmed** failed `MediaRecorder` attempts leak their native recorder; **confirmed** calls longer than four hours are silently truncated; **confirmed** an ON preference can remain visible while no monitor is running after permissions are restored; **likely** ON cannot survive a reboot under the current target-36 service lifecycle.

**Verdict**: NEEDS_CHANGES

## High-level view

The service is started only from a visible activity or the visible Settings flow, which is the correct entry shape for Android's while-in-use microphone foreground-service restriction. It then owns Telephony state, starts on the first OFFHOOK transition, and finalizes on IDLE. A four-hour safety callback stops the recorder without clearing or restarting the active-call state, so the remainder of a longer call is not captured (**confirmed**).

A recording destination is created once per call as a pending `MediaStore` item and reused when VOICE_CALL falls back to MIC. The failed recorder object is not retained until after `prepare()` and `start()` succeed, so an exception from the expected VOICE_CALL attempt leaves that native recorder unreleased before MIC is attempted (**confirmed**).

The preference is committed synchronously before starting or stopping the service, and OFF reaches the active service synchronously to reset the recorder and delete its pending destination. If permissions are revoked while the preference remains ON, however, both launch paths skip or reject monitoring; granting permissions later does not reconcile the already-ON preference with service state (**confirmed**).

The new monitor is `START_STICKY`, but it has no post-reboot activation path. Android target 36 also does not permit a normal `BOOT_COMPLETED` receiver to start a microphone foreground service, so the persisted ON state misses calls after reboot until an allowed foreground activation occurs (**likely**).

## Failed VOICE_CALL setup can poison the MIC fallback

`startRecording()` constructs each `MediaRecorder` inside an `apply` expression and assigns it to the service field only after the entire configure, prepare, and start sequence succeeds. When `setAudioSource(VOICE_CALL)`, `prepare()`, or `start()` throws, the catch block releases `recorder`, but that field is still null. The just-created candidate is therefore abandoned without `release()` (**confirmed**, `CallMonitorService.kt:229-257`).

VOICE_CALL commonly fails for ordinary applications because it requires privileged capture access. That makes this leak part of the normal fallback path rather than an exceptional edge case. The leaked native recorder can retain audio/media-server resources and cause the following MIC attempt or later calls to fail. Keep the candidate in a local variable visible to the catch block, release that exact instance on every failed attempt, and assign it to `recorder` only after `start()` succeeds.

## Four-hour callback ends recording while the call remains OFFHOOK

Both `MediaRecorder.setMaxDuration()` and a delayed handler invoke `stopRecording(discard = false)` at four hours. That publishes the recording and clears recorder state, but `callActive` remains true. No new OFFHOOK transition can restart recording for the same call, and IDLE later finds no destination to finalize (**confirmed**, `CallMonitorService.kt:103-106, 239-248, 313-350`).

This produces a valid but incomplete file for every call over the limit. Remove the cap if full-call capture is required, or roll immediately into a new MediaStore segment and make discovery/upload understand all segments for one call.

## ON can be detached from actual monitor state after permission recovery

`MainActivity` starts the service only when the stored switch is ON and both Phone and Microphone permissions are already granted. `CallMonitorService` also unregisters its listener and returns `START_NOT_STICKY` when either permission is missing. If a user or Android permission auto-reset revokes one permission, the persisted preference remains true; restoring the permission through the app's permission control does not call `setRecordingEnabled(true)` because the switch already displays ON (**confirmed**, `MainActivity.kt:20-26`, `CallMonitorService.kt:116-124`, `RecordingModule.kt:96-132`).

The UI can therefore say ON while every OFFHOOK event is missed until the app is restarted or the switch is cycled OFF and ON. Reconcile desired preference with actual service state after permission results return and whenever the app resumes, while still initiating a microphone foreground service only from an Android-allowed foreground state.

## Persisted ON has no legal post-reboot activation path

The only explicit starts are `MainActivity.onCreate()` and `RecordingModule.setRecordingEnabled(true)`. No boot or other system-event entry point restores monitoring, so a reboot leaves the preference ON but the listener absent until the app is opened (**confirmed** for the missing start path). `START_STICKY` covers service recreation within a boot session, not device reboot.

A direct `BOOT_COMPLETED` fix would still violate Android 15+ restrictions for a target-36 app because microphone foreground services cannot normally be launched from that receiver. The resulting failure to preserve ON across reboot is therefore **likely** to block the stated “every Android OFFHOOK call” behavior unless the product requires a foreground reactivation after reboot or the app qualifies for an Android-supported exemption such as an appropriate dialer/phone-call role.
